# 208 – Více uživatelů, izolace dat v databázi, přihlášení přes Google

**Status:** přijato, 17. 10. 2026

**Kontext:** Aplikace běží na NAS za Cloudflare tunelem (ADR 207) a má sloužit komukoli s Google účtem, každému nad jeho vlastními účty. Dosud byla jednouživatelská až do schématu: z dvaceti tabulek měly `user_id` jen vlastní kategorie, a zhruba 155 dotazů v API s uživatelem nepočítalo. Přidat `WHERE user_id = …` do každého dotazu znamená, že jeden zapomenutý dotaz je únik cizích financí.

**Rozhodnutí:**

- Izolaci vynucuje PostgreSQL row-level security. Datové tabulky dostaly `user_id` s výchozí hodnotou `current_user_id()`, tabulky visící na transakci (přiřazení kategorií, páry převodů, vlastní převody) politiku přes `EXISTS` na transakci. API nastaví `app.user_id` na spojení vyhrazeném pro požadavek (`db.Pool.ScopeToUser`) hned po ověření session nebo tokenu agenta; dotazy v doménách zůstaly beze změny. Bez scope politiky nevrátí nic.
- API nikdy nedotazuje jako vlastník schématu, protože superuser RLS obchází: migrace 008 vytvoří roli `coinbook_app` bez superuser práv a jen s právy na data (bez TRUNCATE, `MAINTAIN` jen na `transaction`), API jí při startu jako vlastník povolí LOGIN se stejným heslem (`db.PrepareAppRole`) a pool se přihlašuje jako ona. Pohledy mají `security_invoker`; komentář v migraci 006 o jednom uživateli platí už jen díky politikám. Start API ověří, že `session_user` RLS neobchází, a akceptační test hlídá, že každá datová tabulka má politiku.
- `agent_token` a `audit_log` politiku nemají: token se hledá podle hashe dřív, než je uživatel znám. Filtrují se explicitně v `agentaccess`.
- Id transakcí hashují i uživatele, aby dva uživatelé se stejným výpisem nekolidovali. Migrace 008 proto odmítne databázi s transakcemi: aplikace je před vydáním, existující data se po resetu naimportují znovu.
- Registrace je otevřená (e‑mail + heslo, nebo Google). Google přes OpenID Connect s `coreos/go-oidc`: authorization code + PKCE + nonce, stav v HttpOnly cookie (SameSite=Lax kvůli návratu z Google). Google účet se nikdy nepřipojí k existujícímu heslovému uživateli: registrace e‑mail neověřuje, takže by si útočník mohl cizí adresu „předregistrovat“ a číst pak data oběti. Shodný e‑mail skončí chybou `email_taken`; propojení z nastavení po přihlášení heslem je možné doplnit později. Uživatel založený přes Google nemá heslo.
- `GET /api/v1/auth/google` a `/callback` jsou v OpenAPI, ale web je otevírá navigací, ne fetch; po návratu web obnoví session z refresh cookie.

**Důsledky:** `make up` nad starší lokální databází vyžaduje `make reset`. Přihlášený požadavek si spojení z poolu vezme až při prvním dotazu (ne během nahrávání souboru) a drží ho do konce; pool má 10 spojení, pro domácí provoz dost. Plánovač s neaktuálními statistikami neumí odhadnout selektivitu politiky a párování převodů pak trvá sekundy místo milisekund, import proto po vložení spustí `ANALYZE transaction` (role má `MAINTAIN`); jeho zámek drží do commitu, takže importy různých uživatelů na sebe po dobu importu čekají, což v domácím měřítku nevadí. Zámek importu samotný je per uživatel. Klasifikátor je cachovaný per uživatel. Limit pokusů o přihlášení počítá na adresu klienta z hlavičky `X-Forwarded-For` (`server.client_ip_header`), kterou Caddy přepíše jedinou adresou podle `CF-Connecting-IP` od cloudflared (`trusted_proxies private_ranges`); klient v domácí síti si adresu může podvrhnout, což doma nevadí; za Cloudflare ho doplňuje Access politika (ADR 207). Otevřená registrace znamená i otevřené nahrávání souborů: originály se ukládají až po úspěšném importu, kvóta na uživatele zatím není. ADR 200 a zadání (jeden uživatel) jsou v tomto bodě překonány.
